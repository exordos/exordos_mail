# Данные и сертификаты

[English](operations.md)

## Постоянные данные в режиме mailbox

ВМ монтирует отдельный том XFS в `/persist`. При замене корневого образа
сохраните этот том и подключите его к ВМ. Сохраняйте весь том в резервных
копиях вместе с владельцами файлов и правами доступа.

| Путь | Содержимое |
| ---- | ---------- |
| `/persist/mail/cyrus/` | Письма, календари, локальные базы и данные Sieve |
| `/persist/mail/postfix/` | Очередь входящей почты |
| `/persist/mail/tx/` | Очередь Postfix TX, ключ DKIM и учётные данные календаря |
| `/persist/mail/control/` | Локальные таблицы адресатов и отправителей, хеши паролей и доверенные IP MX |
| `/persist/mail/rspamd/` | Рабочая директория Rspamd с `rspamd.rrd`. Подключается в `/var/lib/rspamd` через bind mount. |
| `/persist/mail/valkey/` | Журнал AOF с данными Rspamd, включая байесовский фильтр и историю проверок |
| `/persist/mail/tls/` | Сертификаты, закрытые ключи и CA экземпляра |
| `/persist/var/log/` | Системные журналы, подключённые к `/var/log` |

Сокеты и скомпилированные кеши Rspamd создаются заново в `/run` и
`/var/cache`. MetaPaaS передаёт конфигурацию экземпляра, агент обновляет
учётные данные и таблицы адресатов. Включите в резервное копирование
базу MetaPaaS с экземплярами, учётными записями SMTP и ящиками.

Перед заменой корневого образа старой ВМ примените на ней обновлённую
конфигурацию mailbox, пока подключён её старый корневой диск. Сервис
настройки перенесёт предыдущую рабочую директорию Rspamd. Перед заменой
образа проверьте три точки монтирования.

```bash
mountpoint /persist
mountpoint /var/log
mountpoint /var/lib/rspamd
```

После замены образа повторите проверку точек монтирования. Проверьте
сервисы, отправку, доступ к ящику и доставку с внешнего MX. Отложенные
письма на внешнем MX хранятся на его собственном диске.

## Обновление прежнего образа SMTP-only

Перед заменой корневого образа Core поручает агенту перенести на
`/persist/mail` файлы `/etc/exim4/dkim/platform.private`,
`/etc/exim4/exim.key` и `/etc/exim4/exim.crt`, если они есть. Bootstrap
тоже импортирует доступные файлы из этих путей и сохраняет ключи и
сертификаты, уже записанные на томе данных.

Старый Exim доставляет принятые письма из своей очереди. Core ждёт её
опустошения, останавливает приём SMTP и перепроверяет очередь перед
заменой root. Замороженные сообщения также остаются в очереди Exim.
У Postfix свой формат очереди. Новый образ запускается
с подготовленными ключами, а агент восстанавливает логины из MetaPaaS.
Импортированный сертификат SMTP сначала обслуживает прежнее имя. Если
это выпущенный Exim сертификат на сам домен, передайте клиентам SMTP
`/persist/mail/tls/ca.crt` и добавьте его в доверенные перед ротацией:

```bash
sudo /usr/local/lib/exordos-mail/mailbox-tls example.org /persist/mail/tls \
  --migrate-legacy-tx
```

Новый сертификат покрывает `example.org` и `mail.example.org`. Команда
использует существующий закрытый ключ и сохраняет исходный сертификат в
`/persist/mail/tls/tx-legacy.crt`. При переключении обновите настройки
клиентов, привязанных к отпечатку сертификата. Сертификаты, установленные
вручную, обновляйте по процедуре вашего удостоверяющего центра.

## Продление серверных сертификатов

Сертификаты, созданные из образа, действуют для `mail.<домен>`.
RX и Cyrus используют `rx.crt`, Postfix TX — `tx.crt`. Передайте
`/persist/mail/tls/ca.crt` клиентам и внешним MX и добавьте его в
доверенные. Закрытый ключ `ca.key` храните на экземпляре.

Таймер `exordos-mail-tls-renew.timer` запускается ежедневно. За 30 дней
до окончания срока он продлевает сертификаты, выпущенные CA
экземпляра, на 90 дней и перезапускает RX, TX и Cyrus. Перезапуск
может прервать соединения. Внешние MX повторят доставку после временного
сбоя. Продлевайте сертификаты вашей организации через её систему
управления сертификатами.

```bash
systemctl list-timers exordos-mail-tls-renew.timer
sudo systemctl start exordos-mail-tls-renew.service
sudo journalctl -u exordos-mail-tls-renew.service -n 50
```

С внешнего MX проверьте сертификат RX по доверенным на этом MX
сертификатам. Укажите настроенное имя и приватный IP сервера RX.

```bash
openssl s_client -starttls smtp -connect 10.0.0.10:2525 \
  -servername mail.example.org -verify_hostname mail.example.org \
  -verify_return_error -CAfile /etc/postfix/tls/rx-ca.pem </dev/null
```

При обычном продлении под тем же CA менять MX, адресные записи, SPF,
DKIM и DMARC не нужно. Если вы отдельно опубликовали TLSA для DANE
и привязали запись к обновляемому сертификату или ключу, обновите TLSA.

## Замена CA экземпляра

1. Выпустите новый CA и добавьте его публичный сертификат в доверенные
   рядом со старым на всех MX и клиентах. На MX это файл
   `/etc/postfix/tls/rx-ca.pem`. После изменения перечитайте конфигурацию
   Postfix.
2. Установите новый `ca.crt` и соответствующий `ca.key` в
   `/persist/mail/tls/`, сохранив владельцев и права доступа. Запустите
   `exordos-mail-tls-renew.service` для перевыпуска серверных сертификатов.
3. Проверьте TLS с MX и клиентов, а также доставку писем из очереди на
   RX. После перехода всех сервисов на новую цепочку удалите старый CA
   из доверенных.

Если старая ВМ ещё использует самоподписанные сертификаты, созданные
из образа, до замены корневого диска подготовьте на работающей ВМ
CA экземпляра скриптом из обновлённого репозитория.

```bash
sudo bash exordos/images/mailbox_tls.sh example.org /persist/mail/tls --prepare-ca
```

Подставьте домен экземпляра. Добавьте полученный `ca.crt` к существующим
доверенным сертификатам на MX и клиентах. Команда подготовки оставляет
текущие сертификаты RX и TX в работе. После обновления проверьте новую
цепочку и удалите старые записи доверия, когда эти сертификаты перестанут
использоваться.
